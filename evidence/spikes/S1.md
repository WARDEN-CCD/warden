# Spike S1 — supply-chain compatibility (2026-10-21)

**Question:** do the signing and attestation formats chosen in ADR-008/009 verify under Kyverno's
`ImageValidatingPolicy` when stored on GHCR?
**Answer: yes.** With cosign 3.1.4, `actions/attest-build-provenance` v4.2.2 and Kyverno 1.19.2 on Kubernetes
1.37, every policy variant admitted the correctly signed image and refused the unsigned image and the
foreign-signed image, each for the expected reason.

- Harness: [WARDEN-CCD/warden-spike-s1](https://github.com/WARDEN-CCD/warden-spike-s1)
- Runs:
  - [39584076512](https://github.com/WARDEN-CCD/warden-spike-s1/actions/runs/39584076512) — six variants
  - [39585016824](https://github.com/WARDEN-CCD/warden-spike-s1/actions/runs/39585016824) — adds the `full` variant, Rekor kinds, visibility
- Raw evidence: [`S1/`](S1/)

| Item | Version / value |
|------|-----------------|
| Signer | reusable workflow `sign.yml`, cosign v3.1.4 keyless, Sigstore public good |

| Images | `signed` (reusable signer + 3 attestations), `unsigned`, `foreign` (signed from a non-reusable job: valid cert, wrong identity) |

## Admission results (run 39584076512)

| Variant | Checks | signed | unsigned | foreign |
|---------|--------|--------|----------|---------|
| `sig` | signature, exact case-sensitive subject | admit | deny | deny |
| `sig-ci` | signature, `(?i)` subject | admit | deny | deny |
| `prov-stmt` | provenance + `extractPayload(...).predicate.buildDefinition…` repo/ref | admit | deny | deny |
| `prov-pred` | provenance + `extractPayload(...).buildDefinition…` | **deny** (`no such key: buildDefinition`) | deny | deny |
| `sbom` | CycloneDX attestation | admit | deny | deny |
| `vuln` | cosign vuln attestation | admit | deny | deny |

`prov-pred` was the deliberate probe for Q2; its failure on the good image is the answer, not a defect.

Run 39585016824 repeated all six with identical results and added:

| Variant | Checks | signed | unsigned | foreign |
|---------|--------|--------|----------|---------|
| `full` | Warden's draft policy in one IVP: signature + provenance signer + repo prefix (`startsWith`) + `ref == refs/heads/main` + SBOM | admit | deny (`T02/T03/T07: image is not signed by the reusable signer`) | deny (same) |

## Answers

| ID | Question | Answer |
|----|----------|--------|
| Q1 | Does IVP find GitHub provenance and cosign v3 attestations on GHCR? | **Yes.** GHCR's referrers API returns `MANIFEST_UNKNOWN`; all four artifacts (signature, provenance, SBOM, vuln) sit under the fallback tag `sha256-<digest>` as `application/vnd.dev.sigstore.bundle.v0.3+json`, and Kyverno 1.19.2 reads them. |
| Q2 | `extractPayload()` root? | **The in-toto statement.** Paths must start with `.predicate.`. The predicate-root form errors (`no such key: buildDefinition`). |
| Q3 | Rekor entries accepted? | **Yes** with `ctlog.url: https://rekor.sigstore.dev`. All four bundles, including cosign 3.1.4's own *signature* (written as a DSSE bundle with predicate type `https://sigstore.dev/cosign/sign/v1`), carry a `dsse 0.0.1` entry with an inclusion proof in the same log (`logId wNI9atQG…`, the public Rekor v1 log). So cosign 3.1.4's default signing config still targeted Rekor v1 on 2026-10-21; re-test if public-good switches to Rekor v2. |
| Q4 | Certificate subject for a reusable workflow | `https://github.com/WARDEN-CCD/warden-spike-s1/.github/workflows/sign.yml@refs/heads/main` — the **reusable** workflow's ref, org in canonical case `WARDEN-CCD`. Extensions also carry `sourceRepositoryURI` (the caller repo), `sourceRepositoryRef`, `buildTrigger: push`. |
| Q5 | Provenance `externalParameters` shape | `{"workflow": {"repository": "https://github.com/WARDEN-CCD/<caller-repo>", "ref": "refs/heads/main", "path": ".github/workflows/<caller-workflow>.yml"}}`. `runDetails.builder.id` = the reusable workflow ref. |
| Q6 | Release signers for tool checksums | Trivy: `https://github.com/aquasecurity/trivy/.github/workflows/reusable-release.yaml@refs/tags/v0.76.0`; Syft: `https://github.com/anchore/syft/.github/workflows/release.yaml@refs/heads/main` |

## Finding outside the original questions

**GHCR packages pushed by Actions are private, even from a public repo.** The packages API reports
`visibility=private`, and an anonymous manifest fetch returns HTTP 403 ([`S1/package-visibility.txt`](S1/package-visibility.txt)).
Warden's design assumed public images (no pull credentials in clusters). Options are in the "Consequences"
section below.

## Consequences for Warden

1. ADR-008 and ADR-009 move from "Accepted (pending S1)" to **Accepted**. The fallback (legacy `.sig`/`.att`
   layout) is not needed.
2. `warden-policy` IVP drafts are correct in shape — the `full` variant is that draft, and it behaved exactly as
   intended. The `.predicate.` path is now confirmed, and subjects and repo prefixes must use the canonical
   `WARDEN-CCD` (case-sensitive match works). The Rekor v2 risk in ADR-008 did not materialise.
3. `build-sign-attest.yml`: tighten the Trivy/Syft identity regexps to the exact signer workflows above.
4. Image visibility (open, decision needed):
   - **(a)** make each package public once, at `warden new` time. This is a UI step unless an API exists; none was
     found.
   - **(b)** keep packages private: Kyverno `credentials` plus `imagePullSecrets` from a GitHub App token refreshed
     in-cluster.
   - (a) keeps clusters credential-free; (b) keeps "zero manual steps".
